## Evidence states

This is the one authoritative definition of a finding's `verification`. [risk.md](risk.md) uses it for scoring, the API returns it on every finding, and the dashboard and the help article "How Stackurity knows" say the same in plain words.

| State | Definition | Set by | What resolves it |
|---|---|---|---|
| `confirmed` | The installed version was read from an authoritative local source (package database, lockfile, or the exact CDN address or script banner of a front-end library, except copies WordPress core maintains, which are `inferred`; inventory confidence `confirmed`), the asset is reporting, and the version is in the advisory's affected range under the ecosystem's version rules (or its release line has ended). No standing second-check disagreement. | The matcher | Nothing: act on it. |
| `needs_validation` | The match cannot be relied on yet because the installed version was inferred or has low or unknown confidence. Severity is withheld (`unknown`); the score is scaled by 0.7 and the finding is never SOS. | The matcher | `why.missing_information` says exactly what: a confirmed version, for example from the agent. |
| `stale` | The asset has stopped reporting (no report within the stale period, 48 hours by default). The finding was true when the asset was last seen. Scored × 0.8, never SOS. | The matcher, from the asset's collection status | A fresh report: **Check again**, or get the agent reporting. |
| `rejected` | A person marked the finding a false positive with an ignore rule. The matcher keeps it rejected while the rule stands, and keeps its own verdict in `verification_before`, restored on reopening. | A person | Reopen the finding or end the rule. |

**A second-check disagreement is not a state.** It never changes `verification`, so it never lowers the score or priority, never removes SOS and never keeps a finding out of urgent alerts: the second check is deliberately simple, and a defect in it must fail toward alerting. The disagreement is shown instead: the finding page and lists say "Needs validation: the second check disagreed (what differs)", `why.needs_review` is true and `why.missing_information` asks a person to compare the version with the advisory record, the finding carries `second_check: "disagreed"` and `second_check_reason`, and **Home** counts open disagreements to review (`second_check_disagreed` in `GET /findings/summary`). This was the simpler of the two designs considered (the other changed `verification` and exempted disagreements from the risk factors).

What none of them means: a confirmed finding is a confirmed **advisory match**. It says the installed version is in the advisory's affected range. It is not a confirmed exploit and does not show the issue can be exploited on that asset (the code may be unused or unreachable). "Known exploited" means the issue is in CISA's catalogue of vulnerabilities exploited somewhere, not that this asset was attacked.

## Why it matched

Every finding carries `why` (in `GET /findings/{id}` and `GET /findings/{id}/explain`, and in the `explain_finding` tool), built by `internal/why` from what the matcher stored at evaluation time. It is never a re-derivation:

- `sentence`: one sentence, for example "Installed 6.10.0 (from web/package-lock.json, seen 2 h ago) is in the affected range < 7.0.7 of GHSA-xxxx (osv:npm, refreshed 3 h ago), compared with SemVer rules; fixed in 7.0.7."
- A common core: `type` (`package_advisory`, `os_package`, `container_image`, `end_of_life`), `installed` (version, the version compared when it was normalised, where it was read, collector, confidence, when last observed), `source` (deciding record, ecosystem, feed, last successful refresh, stale), `rule` (kind, range, comparator, text, and why it was marked ambiguous), `fixed_version`, `evidence_state` with `evidence_state_text`, `missing_information`, `second_check` and `second_check_text`.
- Type-specific detail: `package` (ecosystem, name, direct, location), `os_package` (release, source package, backport, subscription), `container_image` (image and the inner type), `end_of_life` (product, cycle, end date, latest in cycle). New evidence types add their own block beside the core.

The stored part is compact (`evidence.match`, about 60 bytes per finding): `rule` (`range`, `last_affected`, `no_fix_listed`, `listed_version`; for end of life `exact_cycle`, `version_prefix`, `package_name`, `windows_build`), `record`, and only when they apply `range_type` (`SEMVER`), `backport`, `normalised` and `ambiguous` (`some_records_unreadable`, `sources_disagree`, `version_normalised`, `semver_range`, `version_line_unlisted`: an Oracle Linux advisory lists fixes for several version lines of a package and the installed version is on none of them, so the finding needs validation). Observation times and feed refresh times are read when the explanation is built, so evidence does not change, and findings are not rewritten, on every report. Findings stored before 1.0 have no `match` until they are next evaluated; their explanation says the rule was not recorded.

## Second check

High-impact findings are checked a second time by `internal/secondcheck`, a separate and deliberately simple code path:

- **Which**: open vulnerability and end-of-life findings that are P1, SOS, known exploited, regressed, `needs_validation`, or that the matcher marked ambiguous (`evidence.match.ambiguous`). A partial index (`findings_second_check`, migration 0034) keeps the selection cheap.
- **How it differs from the matcher**: it imports nothing from `internal/intel`, `internal/osv` or `internal/version`. It parses the package URL with its own parser, derives the ecosystem, release and acceptable package names (binary, source package, source RPM, the packages of a kernel, and the kernel source a Debian or Ubuntu signed kernel wrapper such as linux-signed-aws-5.15 or linux-signed-amd64 wraps; metapackages are not mapped) itself, reads the stored affected entries from `advisory_packages` for the finding's group (the ranges and listed versions as the feed published them; the package is in the row's own columns, and severities and other feed-specific fields are not kept there because nothing reads them from it), and compares versions with its own comparators: plain dotted numbers for language ecosystems (pre-releases and words refused), dpkg, rpm (epoch, tilde, caret) and the common Alpine forms. It reads ranges in the order the record lists them, as introduced..fixed spans, instead of sorting events. Paid channels are used only when no free record applies.
- **Results**: `agreed`; `disagreed` with each difference (`affected`, `fixed_version`, `package`, `subscription`, `release_line`, `end_of_life`: what the matcher says, what the second check finds, and a note such as "package identity mismatch" or a distro backport); or `could_not_check` with the reason (a pre-release, SUSE product channels, Ubuntu FIPS builds, a GIT-only range, no stored record, a Windows Azure Edition host or a Windows build outside its own table of update lines). Windows missing-update findings are re-derived from the host's build with its own reading of the update line. Findings on installed Windows programs are re-derived with its own reading of the curated catalogue's data (its own JSON fields, patterns and version formatting, none of `internal/winprograms`' code); a program the catalogue does not match is `could_not_check`. It reads less than the matcher on purpose: what it cannot read is never a disagreement.
- **Effect**: results are stored apart from detection, in `second_checks`, against a hash of the match they checked. A disagreement leaves the finding's verification, priority, SOS and alerts unchanged; it adds a `second_check_disagreed` event, is shown on the finding, in lists and on Home for review, and is logged with the raw inputs in `second_check_disagreements` and the server log, for new corpus cases. When the matcher's claim changes, the check is dropped and runs again; a result for an older claim is discarded. Each result also stores the version of the second check's own rules (`independent.checker`, `store.SecondCheckRules`); results made under older rules are redone, so fixing a rule clears the disagreements it caused.
- **Cost**: a job (`second.check`), never work inside the periodic scheduler, whose few slots a long check must not hold: every minute a periodic task asks, within 5 seconds, whether any finding of the workspace is waiting and queues one job for it (deduplicated); the job checks at most 500 findings, only findings without a current check (a check is redone after 7 days). Evaluation never waits for it, so an urgent alert can precede the check by about a minute. `TestSecondCheckPerformance` (`STACKURITY_PERF_FINDINGS=130000 go test ./internal/secondcheck -run TestSecondCheckPerformance -v`) seeds 130,000 open findings on 2,000 hosts (33,897 of them covered) with a stored advisory record for each issue, and on the development machine (PostgreSQL 17 in Docker, median of 5) measured: choosing a batch 126 ms, a whole run of 500 findings (read, checked and recorded) 0.93 s, the Coverage summary 36 ms, re-evaluating one host of 65 checked findings 65 ms. A first pass over 33,897 covered findings takes about 70 one-minute runs; after that only changed findings are checked.
- **Where it shows**: the finding page, **Coverage** (counts and the latest disagreements), `GET /findings?second_check=`, `GET /second-checks`, and the metrics `stackurity_second_check_findings{result}` and `stackurity_second_check_disagreements_total`.
