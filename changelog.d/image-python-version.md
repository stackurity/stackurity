### Fixed

- **Python inside container images has a version, so an ended Python is flagged.** Images read with `--docker` (running containers, exported through the Docker socket) listed a Python built into the image, such as the official `python` images' `/usr/local/bin/python3.12`, with no version, because nothing in an image is run, and end of life was never checked. The version is now read from the interpreter's files: `include/python3.12/patchlevel.h` (the exact release), else the image's `PYTHON_VERSION` when it is the interpreter's release line, else the release line alone from `lib/python3.12`, reported as `3.12` with evidence saying the patch release is not known. A distribution's own Python stays one component, its package. On hosts the agent still runs `python3 --version` first, and reads the same files when that fails. See [Docker containers](docs/install.md#docker-containers).

### Changed

- **Runtimes are now reported in images with no package database the agent reads (scratch and distroless images).** When an image has no dpkg file lists, apk or rpm database, its runtimes found by path (Python, Node.js, Go, Ruby, PHP, databases and the others the agent recognises) used to be skipped, because the agent could not tell which a package had installed. They are now listed: without a package database no package reports them, so none is reported twice. Python gets its version from its files (above); other runtimes have a version only when their install path gives one, and are listed without one otherwise. Expect new components on such images after the next scan, and end-of-life findings where a version is known. Distroless images' own package list (`/var/lib/dpkg/status.d`) is still not read.
